Module 5

Decision APIs

Language models are good at understanding requests and explaining results. Many business decisions, however, must be consistent, auditable, and sometimes provably optimal. Decision APIs let an agent hand those decisions to services built for them.

About 35 minutes4 Python examplesIntermediate

What is a decision API?

A decision API is a service that receives structured facts and returns a decision, usually with a reason. Examples: approve or reject a request, choose a price or a zone, assign vehicles to routes, or schedule shifts. Inside, it might use business rules, an optimization solver, a predictive model, or a mix.

In an agentic system the work is split: the LLM understands and explains, and the decision service decides. The agent calls the service like any other tool.

Consistency

The same facts always produce the same decision, which a probabilistic model cannot guarantee.

Auditability

Every decision points to a rule or model version that experts own and regulators can review.

Optimality

Solvers find the best plan under constraints, which guessing by intuition cannot.

OpenAPI: describing decision services for agents

The OpenAPI Specification is a widely used, machine-readable format for describing HTTP APIs: their paths, operations, parameters, and JSON schemas. Because a model's tool definition also uses a name, a description, and a JSON schema, an OpenAPI operation maps naturally onto a tool. Several agent platforms can import an OpenAPI document and expose its operations as tools; custom GPT Actions in ChatGPT, for example, are defined with an OpenAPI schema. An OpenAPI-described service can also be wrapped as an MCP server (Module 4).

The example converts a small OpenAPI document for a parking-permit decision service into a tool, then lets a stand-in model call it. Input: the OpenAPI document and a user question. Output: the generated tool schema, the HTTP call, and the decision.

Optimization as a decision API

Assigning three campus shuttles to three routes has only 6 possibilities, so we can check them all. The example shows that choosing "the best option for each shuttle, one at a time" (a greedy choice, similar to what a person or an LLM might do by intuition) can miss the true optimum. Real problems have millions of possibilities, which is why agents should call a solver.

Good practice

  • Let the LLM extract and validate the facts, and ask the user when a required fact is missing.
  • Never let the model invent the decision when a decision service exists. Instruct it to call the tool and report its result.
  • Return a reason or rule identifier with every decision, and log inputs and outputs for audit.
  • Version your rules and models, and evaluate the full agent again when they change (Module 8).
